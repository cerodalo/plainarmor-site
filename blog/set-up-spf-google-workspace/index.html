How to set up SPF for Google Workspace

TL;DR: For Google Workspace, SPF is one TXT record at your domain root: v=spf1 include:_spf.google.com ~all. If you also send mail through other services, add their include: entries into the same single record. Never publish two SPF records.

What SPF does

SPF (Sender Policy Framework) is a public list that says which servers may send mail for your domain. A receiving server looks at the server that delivered a message and checks the list. If the server is not on it, SPF fails.

SPF is one of the two checks DMARC uses. The other is DKIM. For DMARC to pass, at least one of them must pass and align with your From domain.

The Google Workspace record

Google's documentation gives this value for a domain that only sends through Google:

v=spf1 include:_spf.google.com ~all

Reading it:

  • v=spf1 marks it as SPF.
  • include:_spf.google.com says "Google's sending servers are allowed."
  • ~all means "everything else should soft-fail," which receivers usually treat as suspicious rather than rejecting outright.

Check Google's current Admin Help page for SPF before you publish, in case the value has changed.

How to add it

  1. Open the DNS management page where your domain's nameservers point.
  2. Look for an existing TXT record on the root domain (shown as @ or your bare domain) beginning v=spf1.
  3. If one exists, edit it. If none exists, add a TXT record with Name @ (or blank, depending on the host) and the value above.
  4. Save and verify with a lookup:
nslookup -type=TXT example.com

If you see more than one record starting with v=spf1, merge them into one.

Adding other senders

Most small businesses send from more than Google. For each extra service, the vendor gives you an include: value. Add them before the all:

v=spf1 include:_spf.google.com include:spf.vendor.example ~all

(spf.vendor.example is a placeholder; use the value your vendor provides.)

Rules:

  • One record only. Merge, never duplicate.
  • Ten lookups maximum. RFC 7208 limits SPF evaluation to ten DNS lookups. Each include: counts, and nested includes inside them count too. Going over causes an error, and SPF fails.
  • Not every service needs SPF. Many vendors authenticate with DKIM only. Follow each vendor's setup guide.

~all or -all

EndingMeaningWhen to use
~allsoftfailStarting point while you confirm all senders
-allfailWhen you are confident your list is complete
?allneutralRarely useful
+allallow everyoneNever use; it defeats SPF

Under DMARC, the receiver combines SPF and DKIM results with your DMARC policy, so a strict ending is less critical than getting DMARC right.

Common mistakes

  • Two SPF records. Causes a permanent error.
  • Missing v=spf1. Spelled incorrectly or placed after other text.
  • Too many includes. Past ten lookups, SPF breaks.
  • Forgetting old tools. An old newsletter service still sending will fail.
  • Putting SPF on the wrong name. It belongs on the sending domain's root, not at _dmarc.
  • Believing SPF is enough. It is not.

Where SPF falls short

SPF checks a hidden address used in the delivery process (the envelope sender), not the From line people read. So a message can pass SPF and still show a faked From name. That is why DMARC requires alignment between the two. SPF also often fails when mail is forwarded.

A hypothetical example

A small architecture firm at northlight.example uses Google Workspace plus a proposal-signing tool and a newsletter service. Its SPF lists Google only. A DMARC report shows the newsletter service failing SPF. The fix is to add the service's include to the single SPF record (or set up DKIM at the service) before moving DMARC beyond p=none. This scenario is invented.

Do the next step

SPF is half the picture. Turn on DKIM for Google Workspace so you have two ways to pass, then publish DMARC.

Subdomains and parked domains

SPF applies per domain name. A record at example.com does not cover news.example.com, so if you send mail from a subdomain, give it its own SPF record.

If you own domains that never send mail, publish a record that says so, which stops anyone from using them as a sender:

v=spf1 -all

Pair it with a DMARC record such as v=DMARC1; p=reject at _dmarc on that parked domain. These are quick wins because there is no legitimate mail to break.

How to test your SPF afterward

Send a message from a Google Workspace address to a personal mailbox at another provider, open the original headers, and look for a line like spf=pass. The domain named next to it should be your domain or Google's sending infrastructure, depending on how the message was routed. Then test one message from each other tool that sends as you. If a tool shows spf=fail or spf=softfail, check that its documented include is in your single record.

Key takeaways

  • Google Workspace SPF: v=spf1 include:_spf.google.com ~all, verified against Google's documentation.
  • One SPF record per domain; merge other senders into it.
  • Ten lookup limit under RFC 7208.
  • SPF does not protect the visible From line on its own.
  • Pair with DKIM and DMARC.

Frequently asked questions

What is the SPF record for Google Workspace?

Google's documented value is v=spf1 include:_spf.google.com ~all, published as a TXT record at your domain root. Confirm against Google's current Admin Help before publishing.

Can I have two SPF records?

No. Publish exactly one SPF record per domain name. If you use other senders, merge them into the single record.

Is ~all or -all better?

~all (softfail) is a common starting point. -all (hard fail) is stricter. With DMARC in place, both can work, but start soft while you confirm all senders.

Does SPF alone stop spoofing?

No. SPF checks a hidden envelope address, not the From line people see, and it breaks on forwarding. DMARC ties the checks to the visible From domain.
