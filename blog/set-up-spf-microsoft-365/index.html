How to set up SPF for Microsoft 365

TL;DR: For a domain that sends email only through Microsoft 365, publish one TXT record at the domain root: v=spf1 include:spf.protection.outlook.com -all. If other services also send as you, add their includes into that same single record. Check Microsoft Learn for the current wording before publishing.

What the record means

SPF is a public list of servers allowed to send mail for your domain. Microsoft 365 publishes the list of its sending servers behind a single name, so you only need to reference that name:

v=spf1 include:spf.protection.outlook.com -all
  • v=spf1 identifies the record.
  • include:spf.protection.outlook.com means "Microsoft's sending servers are allowed."
  • -all means anything else should fail.

Microsoft's documentation recommends -all for Microsoft 365 domains, because DKIM and DMARC are also in place. It notes that DMARC effectively ignores SPF ~all failures when the message also lacks a DKIM signature. Some administrators still start with ~all while they confirm no legitimate sender is missing; if you do, enable DKIM first.

Do it in four steps

  1. Find where your DNS lives. Microsoft hosts it only if you chose that at setup. Otherwise it is at your registrar or another DNS host.
  2. Look for an existing SPF record. Open the TXT records for the root domain (shown as @ or the bare domain). If one starts with v=spf1, edit it. Do not add a second.
  3. Enter the record. Type: TXT. Name: @ or blank. Value: the line above, plus any other senders (next section).
  4. Verify. From a command line, with your domain in place of example.com:
nslookup -type=TXT example.com

Microsoft notes that Microsoft 365 has no admin portal or PowerShell setting for SPF; you create the record at your registrar or DNS host.

Adding other senders

Insert extra includes before the final all. A hypothetical example with a placeholder vendor:

v=spf1 include:spf.protection.outlook.com include:spf.vendor.example -all

Use only the value each vendor documents. Do not paste IP addresses you saw in a report unless the vendor tells you to.

The ten-lookup limit

RFC 7208 allows at most ten DNS lookups when evaluating an SPF record. Each include: uses at least one, and includes that point to other includes use more, so fewer than ten include: entries does not guarantee you are under the limit. Microsoft's documentation suggests moving outside services to a subdomain with its own record. If you hit the limit, SPF returns an error and receivers treat it as a failure.

Ways to stay under:

  • Remove services you no longer use.
  • Prefer DKIM-only setups where a vendor supports them.
  • Avoid stacking many marketing tools on one domain; consider using a subdomain for bulk mail.

One record, always

Publish only one v=spf1 record per domain name. If you find two, merge them into one line. Two records produce a permanent error.

Mail sent from your on-premises server

If a copier, scanner or old server sends mail directly, it needs to be covered, either by an ip4: entry (for example ip4:203.0.113.10, a documentation address) or, better, by relaying through Microsoft 365. Ask whoever manages the device.

What SPF will not do

SPF checks the hidden delivery address, not the From name people see. It also can fail when a message is forwarded. This is why DMARC requires alignment and why DKIM matters. SPF alone does not stop someone from faking your From line.

A hypothetical example

A small law office at ashgrove.example has Microsoft 365 and an old fax-to-email service. Its SPF lists Microsoft only. The fax service's emails fail. Rather than guess, the office asks the fax vendor for its documented SPF include and adds it to the single record. This is an invented scenario.

What to do next

Enable DKIM for Microsoft 365, then publish DMARC at p=none, and move to enforcement after reviewing reports.

Subdomains and bulk senders

Microsoft's guidance is to use a subdomain for bulk email services you do not directly control, so problems with that mail do not affect your main domain's reputation. Each subdomain needs its own SPF record, because the record for example.com does not cover marketing.example.com.

A hypothetical pair of records, using a placeholder vendor:

example.com            v=spf1 include:spf.protection.outlook.com -all
marketing.example.com  v=spf1 include:spf.vendor.example include:spf.protection.outlook.com -all

This also gives each name its own ten-lookup budget, which helps if your list of services is growing.

How to test your SPF afterward

Send a message from a Microsoft 365 address to a mailbox at another provider, open the original headers, and look for spf=pass. Repeat with a message from each other tool that sends as you. If a result shows permerror, check for two SPF records or too many lookups. If it shows fail for a legitimate tool, that tool's include is probably missing from your single record.

Key takeaways

  • Microsoft 365 SPF uses include:spf.protection.outlook.com.
  • Keep a single SPF record and merge other senders into it.
  • Stay within the ten-lookup limit.
  • SPF alone does not protect the visible From line.
  • Follow with DKIM and DMARC.

Frequently asked questions

What is the SPF record for Microsoft 365?

Microsoft's documented include is spf.protection.outlook.com, giving v=spf1 include:spf.protection.outlook.com -all for a domain that sends only through Microsoft 365. Confirm in Microsoft Learn before publishing.

Does Microsoft add SPF for me?

If Microsoft hosts your DNS, it can set records during domain setup. If your DNS is elsewhere, you add the record yourself at your DNS host.

Why does my SPF show too many lookups?

Each include counts toward a limit of ten DNS lookups in RFC 7208. Remove services you no longer use, or ask vendors about DKIM-only options.

Should I use -all or ~all?

Microsoft recommends -all for Microsoft 365 domains that also use DKIM and DMARC. Make sure your sender list is complete first, and enable DKIM so DMARC can still pass legitimate mail.
